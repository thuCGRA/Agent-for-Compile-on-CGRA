# 固定 II 的覆盖率消融（4x4, II=4, 真实 kernel）

口径：II 钉死在 4（用户给定 II 是编译器的真实用法），4x4，布局来自**同一个生成器**——
每格先用 `-m 0 -i 4` 跑一次纯 A*，把它的放置作为 pin（跨 k 固定），把它的路径作为 bank。
每格 3 次重复，报中位数与 IQR。实例是 A 臂流水线落盘的真实 DFG（`work/armA/<k>/*/dfg/`），
所以和 trace 是同一个 DFG/同一个架构；复制实例不参与本表。

```
config  m0      = -m 0 -i 4，无 pin，A* 自己放置+布线
pins    = 全部节点 pin，不给任何路径（A* 仍决定每一条布线）
k25/50/100 = 全部节点 pin + 该比例的边给出固定路径（RulePolicy, path_mode="bank", rule="critical"）
```

## 结果

| kernel | 节点/边 | m0 | pins | k25 | k50 | k100 | lat(m0→pins) |
|---|---|---|---|---|---|---|---|
| array_add | 20/23 | 1.22s | 0.42s | 0.42s | 0.42s | 0.37s | 11 → 13 |
| conv2d | 39/46 | 2.28s | ✗ 6 冲突 | ✗ | 0.37s | 0.36s | 15 → 17 |
| conv3 | 28/32 | 1.72s | 0.36s | 0.37s | ✗ 4 冲突 | 0.37s | 13 → 15 |
| mac | 22/28 | 1.63s | ✗ 断言 | ✗ | ✗ | ✗ | – |
| mults1 | 25/32 | 2.79s | ✗ 断言 | ✗ | ✗ | ✗ | – |

三档可用的格子里 3 次重复的 IQR 都是 0.00（离散度小于 0.05s）。

## 四条结论

1. **pin 剪枝是真的，而且是单调的，没有 U 形**。array_add 1.22s → 0.42s（2.9x），
   conv3 1.72s → 0.36s（4.8x）。k=25/50/100 之间差别在 0.05s 以内，k=100 甚至略快。
   所以 A 的假设前半段成立（pin 剪枝省时间），后半段"高密度反噬"在这个规模上没出现——
   反噬需要实例大到让布线本身成为主项，而这里耗时被 0.3s 的固定开销和放置搜索支配。
2. **耗时主要由放置搜索决定，不是布线**。m0 比全程 pinned 贵 3–5 倍，而 pinned 的
   0.3–0.4s 里几乎全是流水线固定开销。要让"谁布线"变成可测变量，实例得再大一个数量级
   （≥100 节点），或者把布线器单独计时。
3. **首轮几乎从不通过**（`first_call_ok` 在所有 k>0 的格子里都是 False，`verify_rounds` 都是 2）。
   不是策略布错，而是结构性原因：每张图都有 1–4 条边在端口图上根本不可实现
   （array_add 的 (9,10)/(20018,20017)/(4,5) 是上一轮就定位过的那三条），必须走 flex 让
   A* 自己布。这印证了"覆盖率 100% ≠ 全部接管"。
4. **两个 kernel 在全程 pin 下把 verify 打崩**：
   `Module.cpp:606 getInPort Assertion 'false' failed`（mac、mults1，`pins` 档 0.37s 直接 abort）。
   触发条件是 A* 自己的解里出现 ≥3 段寄存器跳（TREG_RO/TREG_RI 链，日志里 `17->0 (30 ports)`
   那种）。`-m 0` 能产出这种解，但 verify 模式下重走路径时 `getInPort("TREG_...")` 没有对应入口。
   这是 mapper 的限制，不是消融的问题；本表把这两个 kernel 记为"不可用"并给出原因。

## 附带的方法学坑（会误伤结论）

- routeInfo 里的 `-T` 是**相位**（`lat % II`），不是延迟。第一版把 `-T` 当 `lat` 传给 pin，
  结果 8 条 timing 冲突、布线全被拒。正确做法：pin 只给 `t`，让 mapper 自己定延迟；
  slack 排序用的 lat 从 `pins` 档的 report（`placement[].lat`）里取。
- 有些图 A* 的 routeInfo 少一条边（mac 27/28、mults1 31/32），这条边没有 bank 路径，
  用确定性最短路补（本表里它可能就是触发寄存器链的那条）。

## 下一步建议

- 要在 4x4 上拿到有意义的曲线，需要 ≥100 节点的真实 kernel（A 的 traces 里 hpcg / gemm 可能够），
  并且先把 `getInPort` 那条断言处理掉（或把 ≥3 寄存器跳的解标成 flex 而不进 verify 重走）。
- 在拿到大实例之前，"pin 剪枝单调省时"可以直接写：这是一条 3–5 倍的实测收益，
  且不依赖选择哪条边（k=25/50/100 无差别）。

## 四、静态模型错位的三个实例

这三个都真实发生过，写论文的局限性一节可以直接用。共同点：**离线模型和工具链真实语义之间
有缝，而缝里掉下去的东西，现象会伪装成"策略不好"**。

1. **相位被当成延迟**（本轮）。`routeInfo.log` 里每条边的 `-T` 是相位（`lat % II`），不是延迟。
   第一版把它当 `lat` 灌进 pin，结果是 8 条 timing 冲突、所有注入路线被拒——现象上像是
   "规则策略全错"，实际上是口径错。改法：pin 只给 `t`，延迟让 mapper 自己定；slack 排序用的
   `lat` 从 `pins` 档 report 的 `placement[].lat` 取。
2. **工具链谎报 ok**（spike 阶段）。map 成功、二进制落地、`mappingwithlatency.txt` 也写了，
   但仿真 `Mismatches::20`——映射器自检通过不等于仿真一致，寄存器链超过二进制编码上限时
   它照样报成功。所以"ok"只能当必要条件，仿真才是裁判。
3. **R3 的相位假设**（spike 阶段）。第一次算 pin 时按"每条边到达后至少隔一拍"给相位，
   合法解被自己否掉；实际 HyCUBE 同周期转发是常态（2 跳/0 拍实测合法），多跳不花周期。

第 4 个是 §9 的 operand 槽名缺失：静态元数据不足以判断操作数绑到哪个物理端口，
现象是 verify 报冲突而不是给结论。

## 五、oracle / rule / none 的三方对照（口径）

现在表里的 pin 是**神谕 pin**：先跑 `-m 0`，再把它的解当 pin。所以"pin 省 2.9–4.8 倍时间"
测的是**剪枝**，不是**提示**——任何缓存都能做到，与"提示从哪来"无关。写成三方对照才不混淆：

| 设置 | pin 来源 | 回答的问题 |
|---|---|---|
| `oracle` | A\* 自己的解（`-m 0`） | 剪枝的上界：时间最多能省多少 |
| `rule` | 只看 DFG/架构，不跑 A\* | 廉价提示能恢复多少质量（`llm` 行在没有端点前由 `RulePolicy` 代跑） |
| `none` | 无 pin | 基线 |

`oracle` 是 `rule`/`llm` 的天花板。判读规则：`rule` 的 lat 接近 `oracle`、时间也接近，
才算真结论；`rule` 的质量与 `none` 相同、而时间远低于 `none`，那只是"错得快"。
